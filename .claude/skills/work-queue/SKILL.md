# /work-queue

A scheduler around `/next-task autonomous detached`. Every entry runs in its own git worktree and its own fresh subagent, so no entry runs on a context crowded by the last three and no entry's diff mixes with another's. Entries whose declared files do not overlap run at the same time; everything reaches the base branch through one serial merge queue that you alone operate.

**Arguments** — any combination:
- *(none)* — uncapped: until the ending conditions below hold. At most two entries in flight.
- a number — stop starting entries once that many distinct entries have been started, then let the ones in flight finish. A respawn or a second attempt of an entry already started does not count again.
- `-j N` (`jobs N`) — at most N entries in flight. `-j 1` is the serial loop, run through the same worktrees. The repo's machine cap can lower N and never raises it.

## It runs alone

**MANDATORY: this loop never asks the author anything.** No question tool, no pausing to have a disposition confirmed, no "I could do one of three things here." The author started an unattended run and is not at the keyboard — that is the whole point of the mode, and a question does not wait politely, it stops the grind dead and delivers one entry out of seven. Everything the author needs to weigh goes into the final report, where they read it once and act on all of it together.

**An outcome no row below covers is still yours to decide.** The fault table is not exhaustive and never will be; when an iteration ends in a shape it does not name, take the disposition that keeps the base clean and the work retrievable, write which one you took and why into the report, and continue. A gap in this file is a build decision, not a reason to stop — deciding it badly costs one entry, and stopping to ask costs every entry after it.

**The only early stops are the two hard stops below.** Both are conditions of the repo rather than judgements about the work: a base the loop cannot write to cleanly, and a gate already failing on a baseline the loop never touched. Neither is a question — they get reported, not asked. A subagent's report that ends by putting a question to the author is not a stop either: record it for the final report and take the next entry.

## The loop runs only while you call tools

**The harness re-invokes you for exactly as long as your turn ends in a tool call, and stops the moment one does not.** That is the whole mechanism: evaluate, call tools, read the results, evaluate again — and a response carrying no tool call is how the harness learns the work is finished. So an orchestrator that writes `Entry three closed, moving on.` and nothing else has not moved on. It has ended the run, with six entries still in the queue, no error anywhere, and a transcript that reads like a success. This is the commonest way this loop dies and it never looks like a failure from the inside.

**While the run is live, every turn ends in one of exactly two states: a tool call, or at least one spawned agent still outstanding.** The second counts because a finishing agent re-invokes you the same way a tool result does. Nothing else does — not a status line, not a summary between iterations, not a note that you are waiting on something. Narration is fine, but it ships in the same turn as the next call. While entries remain there is always a next call, and if you genuinely cannot name one and nothing is in flight you have reached an ending condition — which is a final report, not a pause.

**A turn is cheap and a stall is not.** Prefer several short turns that each do one thing over one turn that tries to hold a whole integration, and put read-only checks — the queue file, `git status --porcelain` in the main tree and in a worktree, the journal — into a single turn as parallel calls, since read-only tools run concurrently while the state-changing ones are serialised anyway.

## How the parallelism stays safe

Three rules, and every section below is one of them worked out.

**1. One worktree per entry.** `git worktree add <worktree-root>/<slug> -b wq/<slug> <base>`, where `<base>` is the branch checked out when the run started, `<worktree-root>` is `../<repo-name>-wq/` beside the repo — never inside it, where it would show up in `git status` — and `<slug>` is three to five kebab-case words off the entry's heading. If the sandbox refuses writes outside the repo, use `<repo>/.git/wq/` instead, which `git status` never reads either — but many formatters, linters and search tools skip anything under `.git`, so the fresh-worktree gate check before the first spawn has to run at that root, and a gate that checks nothing there is the second hard stop rather than a pass. A worktree gives each entry what the serial loop got from a clean tree: a baseline nobody else writes to, a `git diff` that is only its own work, and a gate run that measures only its own change.

**2. You are the only writer of the queue file and the base branch.** Iterations run detached: they read the queue and return every edit they would have made as a `QUEUE_EDIT` block. You apply those edits, write every marker, and make every commit that reaches the base. Two writers of one file is a lost edit, and nothing ever reports a lost edit.

**3. Nothing reaches the base except through the merge queue** — rebase, apply the queue edit, gate, fast-forward — one entry at a time, in the order they finish. Two entries can each pass the gate alone and fail together, and the gate on the rebased tree is the only thing that catches it. That is why the gate is run at integration, by you, rather than trusted from the worktree.

## Scheduling: what runs together

Entries declare which files they will edit in `**Touches:**` and what must land before them in `**After:**`. `/next-task`'s scheduling-lines section owns the format — read it there rather than keeping a second copy here.

**Every time a slot is free, pick work like this:**

1. **Takeable** means: not carrying `**Needs the author:**`, not in flight, not held in the merge queue, and every `**After:**` heading already gone from the queue file. An `**After:**` naming an entry that is still there but marked leaves this one untakeable too — report it as waiting behind that entry, and do not mark it yourself, since the decision it waits on is someone else's. Match `**After:**` headings ignoring any leading number. **You keep every `**After:**` pointing at a real heading**, so a heading that is nowhere in the file can be read as landed: when you rename a heading, re-point every `**After:**` naming it in the same edit, and when you split an entry, re-point them to its last part. A heading that is still missing and that `git log -S "<heading>" -- <queue>` does not show the queue ever closing — the commit that removed it, not the one that added it is a dangling reference, not a landing — treat the entry as `*` and say so in the report.
2. **Never let `**After:**` lines form a cycle.** Before writing any `**After:**` — from a `depends` outcome, a split, a rename, or the gardener's backfill — follow the chain from the heading you are adding; if it leads back to the entry you are adding it to, do not write it. Mark the entries on the loop with `**Needs the author:**` naming the cycle in full — `A → B → A` — because which of them really comes first is a question about the work, not about the schedule. Check the whole file the same way once before the first spawn, since an author or an earlier run may have written one already: an entry on a cycle is never takeable, and left unmarked it would sit there until the run ended without anyone saying why.
3. **Walk the takeable entries in file order and start each one whose `**Touches:**` overlaps nothing in flight**, until the slots are full. An overlapping entry is passed over for now, not for the run: it starts the moment what it overlaps has landed, ahead of anything below it.
4. **No `**Touches:**` line, or `*`, runs alone.** It starts only with nothing in flight, and while it is the highest takeable entry nothing new starts — let the slots drain, then run it. One lower down holds nothing up. So a queue nobody has annotated degrades to the serial loop rather than to a guess.
5. **In flight means until the merge queue is done with it** — merged, or its branch kept — and an entry resumed to resolve a conflict is still in flight. **A held entry is not in flight**: it takes no slot, does not keep a `*` entry waiting, and does not hold up the gardener. It only blocks entries whose `**Touches:**` overlap it, since those would land on the same author edits.
6. **Overlap is generous.** A directory covers everything under it, a glob covers what it matches, and when you cannot tell whether two lines overlap, they do. The queue file never counts, because no iteration writes it.
7. **Width** is the smaller of `-j` and what the machine cap leaves once everything already running is subtracted — re-checked before every spawn, with the integration gate counted as one more job while it runs.

**Priority still decides.** Parallelism only fills slots that would otherwise sit empty; it never starts a lower entry in place of a higher one that could start.

**The declared files are a forecast, and the merge queue is the guarantee.** A wrong `**Touches:**` costs a rebase conflict and a re-run, never a broken base, so do not spend effort policing the lines before a spawn. Correct them after the fact: an entry that conflicted gets its `**Touches:**` widened with what its pass actually touched, in the same queue commit that records the conflict.

## The queue is yours to curate

A queue is a plan written before the evidence arrived. Working it produces evidence, and a loop that may not act on that evidence spends its run executing a plan it can already see is wrong. Both moves below are decisions, taken and named in the report — never questions. **Every entry you write carries scheduling lines**, and that includes the ones you write from an iteration's `NEW_ENTRIES`.

**Queue what you find broken.** An iteration that turns up a real defect no existing entry will reach — a dead link, a doc addressing the repo from a directory it no longer occupies, a reference to a renamed section, a lever documented against a key that does not exist — gets an entry, written in whatever shape the repo's own entries use. **Verify the defect yourself before writing the entry**, because a subagent's write-up is a claim; count the broken links, resolve the path, check the key. Prefer fixing it inside the entry that already owns that ground, and open a new one only when nothing does. The test for whether it belongs in the queue at all is whether some entry would otherwise reach it: a defect every future pass will step over by construction is exactly the one that needs queueing, and the standing entries are usually the ones stepping over it.

**Re-sort on evidence, and standing entries are what force it.** A standing entry — one that never closes, that carries itself forward batch by batch — sits wherever it was last put, and if that is the top it re-selects itself for the rest of the run while everything under it starves. Watch for an entry that has been taken twice with the rest of the queue untouched, an entry whose own text names a condition for being taken that is not currently met, and an entry that a landing has just made cheaper or more urgent. Move it, and **move it by position rather than by marker** where the repo treats position as priority — the markers mean "faulted" and "needs a decision", and borrowing one to mean "not yet" corrupts the two signals scheduling reads.

**What re-sorting is not.** Reordering an entry is not rewriting what it means, and adding a repair entry is not deciding a design question — a fork still gets queued unanswered for the author. Never delete an entry the author wrote on your own judgement — the one deletion you apply is an iteration's `REWRITE: delete`, after checking yourself that what it calls obsolete is. If moving an entry falsifies a sentence inside it, fix that sentence in the same pass and say so, because the entry's own text often explains its position and goes stale the moment it moves. If a rewrite changes a heading, fix every `**After:**` that names it in the same edit.

## The gardener pass, and it runs every time

**MANDATORY: every run ends with one gardener pass, and a run that closed three or more entries takes one mid-run as well.** A queue drains toward whatever was already in it, so a loop that only ever executes entries leaves the repo tidier and no better aimed. The gardener is a fresh `general-purpose` subagent — **never a `fork`** — whose whole job is to look at what the run actually produced and leave behind a queue pointed at improving the thing the repo measures. It writes entries and it restructures the queue file. It implements nothing.

**It gets three jobs and they are read in this order.** First, **validate what the run landed**: hand it the run's commit range and let it read the diffs against the repo's own rules, looking for the failures those rules exist to catch — a constant or floor added to move a figure, a mechanism the docs do not describe, a lever tuned toward a measurement, a doc left contradicting the code, a figure quoted into a permanent doc that the run's own output does not support. Entries that landed side by side never saw each other's diffs, so a contradiction between two of them is exactly what this read is for. Second, **propose work that would improve runs**: take the outcomes the repo's own docs name as what it is tuned against, read the current findings for which of those are failing, unmeasured, or resting on a stale reading, and write entries that would move them. Third, **backfill scheduling lines** on any entry that lacks them, from the entry's own grounding and the code it names, writing `*` where it cannot tell — including `**After:**` wherever one entry's Do needs what another's creates, which is the dependency a disjoint `**Touches:**` would otherwise let run early. The second job is the point; the first is what stops it building on sand; the third is what lets the next run go wide.

**The hard limits, and they are what make this safe to run unattended.** It may not invent design. **No entry it writes may propose a mechanism the docs do not already describe**, and where it finds that the obvious next step needs a decision, that is a fork: it gets queued unanswered and marked for the author in whatever way the repo marks such things, never resolved and never softened into prose that reads as settled. It may not delete or reverse an entry the author wrote, may not weaken a prohibition list, and may not decide a tuning lever by argument — a lever gets an entry proposing a sweep, not a value. Every entry it writes matches the shape the repo's own entries use, including any rule the repo has about figures, numbering or length. **Aiming at an outcome is not the same as tuning toward it**: an entry that proposes measuring whether a pillar works is inside the line, and one that proposes making a number land is the exact thing the repo's rules forbid.

**Restructuring is allowed and is bounded by the same rules as re-sorting.** It may reorder, group, split an overlarge entry, or rewrite a standing entry's own account of its state — subject to position meaning priority where the repo says it does, to markers keeping their meanings, and to naming in its report every entry it moved with the evidence that moved it. Where a repo forbids numbering its entries, it does not reintroduce numbers.

**Verify before you commit any of it.** Its proposals are claims, exactly as an iteration's report is a claim. Check each defect it names against the code or the doc it points at, check that each new entry's premise is true, and spot-check a few backfilled `**Touches:**` lines against the code they claim — a gardener that misreads a findings section will write a confident entry aimed at nothing. Cut what does not survive that check, keep the rest, and say in the report which you cut. **The queue restructure is its own commit**, separate from any entry's commit, so the run's history keeps executing work and re-aiming the queue distinguishable.

**It never runs while anything is in flight.** It writes the queue file in the main tree — give it the main tree's path as its repo — which makes it a second writer unless it is the only thing running. To take the mid-run pass, stop starting entries, let every one in flight finish and go through the merge queue — held entries excepted, since only the author can release them — then spawn it — and start scheduling again only once its commit has landed. **"It reported and stopped" is not finished.** A pass you resumed once can be woken again by its own stranded validator or a message of yours arriving late; treat an iteration as finished only when its report has arrived *and* nothing of it is still outstanding.

## The merge queue, and why you commit

**Each closed entry lands as one commit on the base: its code and the queue edit that closes it, together.** That keeps `git log --oneline` the run's record, makes every commit on the base a gated one, and means no entry's code ever lands without the entry going with it. Match the repo's commit convention — run `git log --oneline -5` and copy what is there. **Never push.**

**When an iteration's completion arrives, integrate it before you look at anything else**, one at a time, in the order they finish. With `W` its worktree and `wq/<slug>` its branch:

1. **Read the state yourself, in one turn:** the report's `QUEUE_EDIT` block, `git -C W status --porcelain`, `git -C W diff --stat`, `git -C W log --oneline <base>..HEAD`, `git status --porcelain` in the main tree, and the journal. The report is a claim; the worktree is the evidence. **Commits on the branch are work** exactly as uncommitted changes are — a pass that committed despite being told not to has not left an empty worktree. Copy the `QUEUE_EDIT` block into the journal now; step 3 may need to apply it more than once.
   - **The queue file shows as changed in `W`, uncommitted or in its commits** → the pass broke detached mode. With `<fork>` = `git -C W merge-base HEAD <base>` — the base has moved since the spawn, so the branch name alone no longer marks where `W` started — save `git -C W diff <fork> -- <queue>` into the journal directory, then `git -C W checkout <fork> -- <queue>` and commit that in `W` — its edit is preserved in that file, and from here it is only a claim like the rest of the report.
   - **Diff the main tree against the spawn snapshot**, `git diff <snapshot>`, to see exactly what changed in it while this pass ran. A changed path that now holds exactly what the same path holds in `W` — compare with `git hash-object` — is a leak whose work the branch already has: stash it, labelled with the run and the entry, and charge the leak as the fault table says. A changed path inside this entry's `**Touches:**` or `TOUCHED` that `W` did *not* change is a **possible leak** — the pass may have written to the main tree instead of its worktree, or the author may be working there. You cannot tell which, so leave it in place, charge nothing for it, and name it in the report as a possible leak from that entry. Any other main-tree change is the author's, and you leave it alone.
2. **Classify it by `QUEUE_EDIT` against what `W` actually holds**, using the outcome rows below.
3. **To integrate code:**
   1. Stage what `git -C W status --porcelain` shows **except the setup leftovers** the fresh-worktree check recorded before the first spawn — environments, caches, anything the repo's setup creates that it does not ignore — then `git -C W commit -m "<one line>"`, folding any commits the pass made into this one with `git -C W reset --soft $(git -C W merge-base HEAD <base>)` first, so the entry stays one commit.
   2. `git -C W rebase <base>`. A conflict → `git -C W rebase --abort`, which puts the branch back exactly as committed, and take the conflict row in the fault table.
   3. Apply the queue edit to the queue file **in `W`** — the base's latest version is what the rebase just put there, since no iteration writes it — then `git -C W add <queue> && git -C W commit --amend --no-edit`. Amending is safe: the branch has never left this machine.
   4. **Run the gate in `W`.** It passes → go on, but first look at `git -C W status --porcelain` again: a tracked file the gate rewrote — a formatter — gets amended in and the gate run once more. It fails → the entry did not close, whatever its report says: take the gate row in the fault table.
   5. `git merge --ff-only wq/<slug>` in the main tree. Refused because the base moved underneath you — the author committed — → **take the queue edit back out before rebasing again**, which works only because sub-step 1 left the entry as one commit: `git -C W checkout HEAD^ -- <queue> && git -C W commit --amend --no-edit`, then return to sub-step 2 and re-apply it from the journal. A rebase carrying the old queue edit conflicts with every queue-only commit that landed since, for a clash the entry never caused. Refused because the main tree holds the author's own uncommitted edits to files this commit changes → the entry is **held**: leave the branch and worktree as they are, and retry after every later integration and whenever nothing else is in flight. Never stash the author's work to make a merge go through.
   6. **Before removing `W`, save what removal would delete.** `git worktree remove` takes ignored files with it: if the report says the pass wrote results to an ignored path, or `git -C W status --porcelain --ignored` shows ignored files outside the setup leftovers, copy them into the journal directory. Then `git worktree remove W` and `git branch -d wq/<slug>`. `-d` refuses an unmerged branch, which is the point of using it. If removal refuses because untracked files remain, skip the `branch -d` too — the branch is still checked out there and it would fail — leave both in place, record them in the journal, and report them. Never `--force`.
4. **A queue edit with no code** — a block, a rewrite, a split with nothing closed, an attempt marker, a new entry — is committed straight onto the base from the main tree, **staged by explicit path**: `git commit -m "<one line>" -- <queue>`. Never `git add -A` in the main tree; it may be holding the author's work. Then remove the worktree; if it holds anything at all, keep its branch by the preservation rule below.

**Outcome rows** — what `QUEUE_EDIT` says, checked against `W`:

- **`close`, with a diff** → integrate the code with the entry deleted and anything that pointed at it re-pointed.
- **`close`, empty diff** → a `done` verdict. Check it yourself with a `git log` and a look at the code; if it holds, delete the entry with a queue-only commit, and if it does not, give the entry its next attempt.
- **`block`** → write `**Needs the author:**` with the questions under it, queue-only commit. Record the questions for the final report.
- **`rewrite`** → apply it and move the entry to `NEW_POSITION`, queue-only commit. A rewrite that changes the heading renames the entry in the ledger too. `REWRITE: delete` is applied only once you have checked the obsolescence yourself, and charges nothing, since nothing is left to charge. **Any other rewrite costs the entry an attempt, exactly as a fault does** — see the rewrite rule below. A pass that produced no code is not progress just because it produced prose.
- **`split`** → replace the entry with its parts. With `CLOSED`, integrate that part's code and leave the closed part out of what you insert; its successors' `**After:**` then names a heading that has landed. Without `CLOSED`, it is a queue-only commit and the split is charged as an attempt: the first part carries `**Attempted once:**` naming the split, and the other parts start at zero. A split is real progress only if a part then closes, so a first part that comes back split or rewritten again has had its second attempt, and gets `**Needs the author:**` — the whole entry is underspecified rather than large.
- **`depends`** → the pass found the entry needs something another queued entry adds, and stopped before building it. Check each `DEPENDS_ON` line yourself: the named entry is in the queue, its Do creates what this one needs, and that thing is absent from the base. Each that holds goes into the entry's `**After:**`, through the cycle check above, in a queue-only commit; one that does not hold is dropped and named in the report. If nothing holds, the entry gets an attempt as a no-op pass would. **A dependency that holds charges nothing** — the entry was right and only early, and it is the scheduler's job to have known. The entry becomes takeable again the moment what it waits on lands. An entry that comes back `depends` a third time in one run is not converging, and that third return is charged as an attempt.
- **`NEW_ENTRIES`, alongside any of these** → verify each defect yourself and add the ones that hold, in the same commit as the rest of the edit.
- **`VALIDATION: fail`, whatever the rest says** → the validator never cleared it, and `/next-task` does not close what a validator has not cleared. Never integrate it on the strength of the gate, which does not read prose: take the abandoned-implementation row.
- **No block at all, or `none`** → read `W` and take the matching fault row.

**Wait for the agent to actually finish before you integrate**, even once its report looks final. A pass can keep applying its validator's nits after it writes its block, and its worktree is only yours once its completion notification has arrived and nothing of it is outstanding. If a finished iteration wakes after you removed its worktree and writes into the path again, leave what it wrote, delete nothing, and report it.

## Spawning an iteration

**Spawn one subagent per entry, in the background**, as soon as scheduling gives it a slot. Create its worktree first, then `Agent` with `subagent_type: general-purpose`, **never `fork`** — a fork inherits your context, which is the thing this loop exists to avoid.

**Keep the prompt short.** The main tree's path and the worktree's path; that it works only inside the worktree, which is its repo; the queue file path inside the worktree; which entry, by heading, it invokes the `next-task` skill on in `autonomous detached` mode; its share of the machine budget; and that it returns that skill's step 7 report verbatim, `QUEUE_EDIT` block included. Do not summarize the entry, do not say what you expect it to find, and do not paste the repo's `CLAUDE.md` — it reads that for itself, and a paraphrase costs more than the original.

- **A spawned agent already runs in the background — there is no flag for it and none to get wrong.** `Agent` returns as soon as the subagent is launched and the harness re-invokes you when it finishes. With several in flight, each completion wakes you separately; integrate that one, fill the free slot, and end the turn.
- **Name the entry by its heading, never by a number.** Positions move with every landing, and with several entries landing out of order a number is wrong almost immediately.
- **The `description` says what the work is.** Three to five words off the heading — `Portable pow for determinism`, `Delete tag synergy stub` — the same words your one-line iteration note leads with, and the same words as the slug, so a watcher reads one name everywhere.
- **Let the iteration inherit your model, and buy the cheap agents cheap.** An iteration reads a repo, writes code and argues with a validator, so pass no `model`. The gardener reads diffs against the repo's rules and writes the next run's entries, the one place a run should not economise.
- **Require the close-out before the report, in every prompt.** Say plainly: finish the pass — the `QUEUE_EDIT` block is its close-out — in the turn the validator's verdict wakes it into. Then say how the wait works, because the wrong reading of "wait" is what burns a run: ending a turn with no tool call while its validator is live *is* the wait, and the harness re-invokes it with the verdict; staying inside the turn is not possible without polling. If it is ever awake without the verdict, it asks the validator by `SendMessage` to its `agentId` to restate it and ends the turn again.
- **Snapshot the main tree at the spawn with `git stash create`**, which records the dirty state as a commit without touching the tree, and put its ref in the journal (an empty result means the tree was clean, and `HEAD` is the snapshot). It records contents rather than paths, which is what step 1 of the merge queue needs to tell a leak from the author's own edits.

**Wait for an iteration, never watch one.** There is nothing to poll: no `sleep` loop over `seq`, no grep for `"type":"result"`, no `tail -f`, and no reading the `.output` path the spawn returned — that file is the agent's full JSONL transcript, and reading it floods the context this loop exists to keep empty. **While iterations run, you can still work** — integrate the one that just finished, check machine load, verify a defect a report claimed, answer the author. When there is genuinely nothing to do, say so in one line and end the turn — safe only because something is outstanding. Do not invent work to fill the wait.

Emit one short line per integration as you go — the entry, its outcome, and what is in flight now — so anyone watching can follow without reading the transcript. It is output, never a checkpoint.

## Your context will be compacted, so the run's state lives in a file

**An uncapped run outlives its own context window.** When the window fills the harness compacts it, and the small factual details — an attempt count, a kept branch, which worktree belongs to which agent, the `HEAD` the run started at — are precisely what a conversation summary drops. The loop then grinds on with confident wrong state, and with several agents in flight a forgotten one is a worktree nobody integrates.

**So the run keeps a journal, and the journal is the state — your context is only a cache of it.** Write it to the session scratchpad, **never inside the repo**. One file, rewritten whole whenever anything in it changes, holding:

- The base branch and its starting `HEAD`, the main tree's path, the worktree root, the queue file path, the gate command and the exemptions the repo grants it, the machine cap and the width.
- The entry headings in file order as they stood at the start, and every commit the run has landed with the entry it closed.
- **The in-flight table:** each entry in flight with its slug, worktree, branch, `agentId`, `**Touches:**`, and the main-tree snapshot taken at its spawn. Plus anything held in the merge queue and why.
- The attempt ledger: each entry attempted, how many times, and what the fault was each time — conflicts listed separately, since they charge nothing.
- **Every branch the run kept, and every stash it made**, with what is on it.
- Every `**After:**` line the run added and why, with a count of `depends` returns per entry.
- Every entry stepped over for the author's marker, every entry waiting on a marked `**After:**`, every entry the loop added, and everything re-sorted or split.
- Whether the mid-run gardener pass has already run.

**Read it back with the queue file and the main tree's `git status` whenever you schedule or integrate.** Together they are the whole truth about the run. Never answer a question about the run from memory when one of them can, and after a compaction treat memory as empty rather than as stale — rebuild the in-flight table from `git worktree list` and the journal, never from recollection.

**This does not retire `**Attempted once:**` in the entry.** The journal dies with the session; that marker is in the repo and is the only part of the ledger a *later* run can read back.

## Before the first spawn

1. **Read `CLAUDE.md` and find the queue exactly as `/next-task` step 0 does** — that step owns the resolution order, so do not keep a second copy of the list here. **No queue means no run:** say where you looked and stop without spawning anything.
2. **Look at the main tree, and leave the author's work where it is.** (Mid-run, a queue file that turns dirty in the main tree when neither you nor the gardener has an uncommitted write to it in hand means the author is editing it now. Stop starting entries, integrate nothing that touches the queue, keep in-flight work on its branches, and take the first hard stop: two writers of the queue is the one thing this design cannot absorb.) Worktrees mean another entry's diff can no longer leak into a validator's, so uncommitted edits in the main tree no longer block the run. Two exceptions. The queue file must be clean, since you are about to become its only writer: if it is dirty, stash that one path, labelled, and report the stash. And note every other dirty path in the journal, because the merge queue reads new dirt against it.
3. **Find leftovers from a dead run.** `git worktree list` and `git branch --list 'wq/*'`. A worktree whose directory is gone gets `git worktree prune`; one that still holds work is kept and reported, never removed with `--force`. A new entry whose slug collides with a kept branch or a worktree directory still present gets `-2` on the end of both.
4. **Find the gate and hold the machine cap yourself.** Two things out of `CLAUDE.md`. The gate is the command the repo says a change has to pass, plus which kinds of change it exempts. The cap is whatever the repo says about how much of the machine a run may take. **That cap counts every session at once, not every subagent separately.** Your subagents cannot see each other, the author's own work, or a second loop in another terminal, so the checking is yours: run whatever the repo names before each spawn, subtract what is already running, set the width from what is left, and pass each spawn its share. Parallel entries multiply every cost the cap exists to bound, and the cap is not raised because the loop got wider.
5. **Prove the gate on a fresh worktree of the base before the first spawn**, at the worktree root the run will actually use. Create one, set it up the way the repo's docs say, run the gate there, **record what setup and the gate leave untracked** — those are the setup leftovers the merge queue never stages — then remove it. This is both the baseline check and the proof that the repo works from a fresh checkout at all — a gate that passes in the main tree and fails in a worktree is reading something gitignored, and every entry would fail for it. Either failure is the second hard stop.
6. Note the starting `HEAD` and the entry headings in file order. **Read back any attempt markers already in the file.**
7. **Open the run journal**, in the session scratchpad and never in the repo, and put everything above into it.

## Faults recover, they do not end the run

**A fault costs the offending entry its turn, never the run.** Two attempts is the limit: on the second fault for the same entry, it gets the `**Needs the author:**` marker with the reason written into it, and the loop moves on.

**Write the first attempt into the entry too, not only into the ledger.** One line reading `**Attempted once:**` and what the fault was, committed queue-only onto the base. It is the only part of the ledger a restarted run can read back.

**A rewrite is an attempt.** An iteration that ends with the entry rewritten, re-sorted or split — and no code — is charged the same as a fault. On the second such iteration for the same entry, stop believing it is merely stale: **an entry rewritten twice is underspecified, not out of date**, and the marker becomes `**Needs the author:**` with one line naming what could not be settled from the entry and the docs it links. A stale verdict sends `/next-task` back without implementing, by design, so an entry whose figures drift comes back rewritten every visit — and if a rewrite is scored as progress, it sits in the queue being polished for as long as the loop runs.

**A conflict is never the entry's fault.** It is the scheduler's: two forecasts that missed each other. It charges nothing.

**`**Attempted once:**` is not the author's-call marker and must never be written as one.** Scheduling keeps selecting an entry that carries it; only `**Needs the author:**` stops it.

**The preservation rule, in every recovery: never discard.** No `git reset --hard`, no `git checkout --` on a file you have not saved first, no `git stash drop`, no `git worktree remove --force`, no `git branch -D`, no deleting a file to make a build pass. **Keeping work means keeping its branch:** if the branch carries a queue edit of yours, take it out first (`git -C W checkout $(git -C W merge-base HEAD <base>) -- <queue>`), so a later restore does not conflict on it; stage everything but the setup leftovers, as merge-queue sub-step 1 does, and `git -C W commit -m "wip: <heading> — <fault>"`; save ignored results as sub-step 6 does; then `git worktree remove W` on the now-clean worktree. The `wq/<slug>` branch stays, recorded in the journal and named in the report. **Every removal of a worktree, on any path, saves ignored results first.** That is three commands with no judgement in them, so you run them yourself rather than spawning anyone. A stash is only for the main tree — the queue file at the start, or a leak — and is labelled with the run and the entry.

| Fault | Recovery |
|---|---|
| Rebase conflict at integration | Charge nothing. Resume the same iteration once by `SendMessage` to its `agentId`: rebase `W` onto the base, resolve, and finish with `git rebase --continue` — say plainly that it may make the rebase's commits, which its detached mode otherwise forbids — then re-run the gate and report again. It holds the change in context and resolves far more cheaply than a fresh pass. If that fails, keep the branch, widen the entry's `**Touches:**` with what its pass touched, and schedule it alone next time. Conflicting twice is not a fault either, but the second time it runs alone. |
| Gate fails at integration | Merge nothing. Keep the branch. If the base gained commits the loop did not make since the last gated integration, first run the gate on a fresh worktree of the base: if that fails too, it is the second hard stop, and the entry is charged nothing. Otherwise charge the attempt and mark the entry with what failed. |
| Work in `W`, no `QUEUE_EDIT` or `VALIDATION: pending`, and the gate passes in `W` | The pass stopped at its validator. Charge nothing. Resume it once by `SendMessage` to finish the pass and return its block; if it comes back with `close`, integrate. If it cannot, integrate the code anyway, leave the entry standing with `**Attempted once:**` naming what validation flagged, and say so in the report — the next verifier sees the code is in and closes the entry in one cheap pass. Keeping finished work on a branch instead would conflict with every later entry touching those files. |
| Work in `W` and no entry closed, and the gate fails in `W` or `VALIDATION: fail` | An implementation abandoned partway, or one its validator would not clear. Keep the branch, charge the attempt, write the gap the report names into the marker. |
| An iteration returned no report at all — the agent died, hit a limit, or was cancelled | Not the entry's fault until `W` says otherwise. Nothing in `W` → remove it and respawn once **without charging an attempt**. Work in `W` → whichever row matches it. Twice in a row on the same entry with nothing changing: mark it and move on. If the next spawn dies the same way, it is the harness rather than the queue — stop starting entries, let the rest finish, and report that. |
| The report and `W` disagree — it claims a close with nothing in `W`, or a diff it does not mention | Believe neither. Keep any work on its branch and give the entry its second attempt with a fresh subagent and a fresh worktree. |
| `QUEUE_EDIT: none` with nothing in `W` | Second attempt. If it no-ops again, mark it and move on. |
| An entry rewritten twice, whether in this run or according to the marker already in the file | Keep the second rewrite, mark `**Needs the author:**` naming what could not be settled from the entry and its docs, and move on. |
| The pass leaked into the main tree | Stash the leaked paths, labelled. Then whichever row `W` matches, plus an attempt for the leak itself. |

**Nothing in this loop bisects or reverts its own commits.** Every commit on the base passed the gate on exactly the tree it landed as, so a broken entry never lands.

**Two hard stops**, and both are stops because continuing past them produces work that only looks done:

- **The base cannot be written cleanly.** The queue file in the main tree will not come clean after two attempts, or worktrees cannot be created. Stop starting entries, keep every in-flight entry's work on its branch, report the exact state, and touch nothing further.
- **The gate fails on a base the loop has not touched** — at the fresh-worktree check before the first spawn, or at integration on a base that someone else moved. Do not bisect, do not revert, and do not carry on: every later integration would fail for a reason none of the entries caused, and grinding forward would mark the whole queue for it. Keep in-flight work on branches and report the exact failure.

## When the run ends

**Whichever way a run ends, [the gardener pass](#the-gardener-pass-and-it-runs-every-time) runs before the report** — including a run that closed nothing and a run that stopped on a cap. The two hard stops are the only exception.

**Re-derive the ending condition from the queue file and the journal every time you test it**, never from a sense that the run has gone on a while.

These are ends, not faults:

- **Nothing is in flight, every held entry has been retried once since the last integration and refused again, and nothing is takeable except entries whose only obstacle is overlapping a held entry.** A held entry waits on the author's own uncommitted edits, which an unattended run cannot clear, so it ends the run with its branch and worktree kept and the blocking paths named, and the entries stuck behind it are reported with it. Takeable is scheduling's definition, so an entry that is merely overlapping something in flight is not an end — it is next. Name every entry left in the queue in the report with what it waits on: the author's marker, a marked `**After:**`, or a cycle.
- **An entry cap was given and has been reached, and everything started has gone through the merge queue.** With no argument there is no cap — do not stop an uncapped run because it feels long or because several entries have closed.

## Report

Lead with what closed and why the run ended. Then:

- Each closed entry with its commit, and that the gate passed on the rebased tree before it landed. Name any entry where the gate was skipped and the repo rule that allowed it.
- **Everything waiting on the author, as the actual questions, in queue order.** This is the part the author is reading for.
- **Every branch the run kept and every stash it made, with what is on each.** Work moved out of the way and never mentioned is work lost in practice.
- Every fault, what it recovered to, and which entries were marked rather than done. Every conflict, and the `**Touches:**` lines you widened because of it.
- How wide the run actually went — the most entries ever in flight at once, and what held the width down: unannotated entries, overlaps, `**After:**` chains, or the machine cap. That is what tells the author whether annotating the queue better would buy anything.
- Anything held because the author's uncommitted edits blocked a merge.
- Every dependency the run discovered — each `**After:**` it added from a `depends` outcome, with what the entry needed — and every cycle it found and marked.
- Anything re-sorted or split, and where it moved, with the evidence that moved it.
- **Every entry the loop added, with the defect that justified it and how you verified that defect.**
- **What the gardener pass found and what it left** — anything it flagged in landed work, every entry it added with the evidence you checked, everything it moved and why, which scheduling lines it backfilled, and what you cut. Say plainly which of the outcomes the repo is tuned against are now aimed at by an entry and which are still unaddressed.
- The queue as it now stands, and the range of commits the run produced.
- **Where the run journal is.**

Never spin a recovered fault as a success or a short run as a finished one. If a capped run ended early, say so in the first sentence. If an uncapped run stopped with takeable entries still in the queue, that is not an end — say in the first sentence why it stopped and what is left.
