# /work-queue

A thin loop around `/next-task autonomous`. One entry per iteration, each in its own fresh subagent so no entry runs on a context already crowded by the last three.

**Arguments:** *(none)* runs uncapped — until the queue is empty or every remaining entry is the author's call. A number caps at that many iterations.

## It runs alone

**MANDATORY: this loop never asks the author anything.** No question tool, no pausing to have a disposition confirmed, no "I could do one of three things here." The author started an unattended run and is not at the keyboard — that is the whole point of the mode, and a question does not wait politely, it stops the grind dead and delivers one entry out of seven. Everything the author needs to weigh goes into the final report, where they read it once and act on all of it together.

**An outcome no row below covers is still yours to decide.** The fault table is not exhaustive and never will be; when an iteration ends in a shape it does not name, take the disposition that keeps the tree clean and the work retrievable, write which one you took and why into the report, and continue. A gap in this file is a build decision, not a reason to stop — deciding it badly costs one entry, and stopping to ask costs every entry after it.

**The only early stops are the two hard stops below.** Both are conditions of the repo rather than judgements about the work: a tree that will not come clean, and a gate already failing on a baseline the loop never touched. Neither is a question — they get reported, not asked. A subagent's report that ends by putting a question to the author is not a stop either: record it for the final report and take the next entry.

## The queue is yours to curate

A queue is a plan written before the evidence arrived. Working it produces evidence, and a loop that may not act on that evidence spends its run executing a plan it can already see is wrong. Both moves below are decisions, taken and named in the report — never questions.

**Queue what you find broken.** An iteration that turns up a real defect no existing entry will reach — a dead link, a doc addressing the repo from a directory it no longer occupies, a reference to a renamed section, a lever documented against a key that does not exist — gets an entry, written in whatever shape the repo's own entries use. **Verify the defect yourself before writing the entry**, because a subagent's write-up is a claim; count the broken links, resolve the path, check the key. Prefer fixing it inside the entry that already owns that ground, and open a new one only when nothing does. The test for whether it belongs in the queue at all is whether some entry would otherwise reach it: a defect every future pass will step over by construction is exactly the one that needs queueing, and the standing entries are usually the ones stepping over it.

**Re-sort on evidence, and standing entries are what force it.** A standing entry — one that never closes, that carries itself forward batch by batch — sits wherever it was last put, and if that is the top it re-selects itself for the rest of the run while everything under it starves. Watch for an entry that has been taken twice with the rest of the queue untouched, an entry whose own text names a condition for being taken that is not currently met, and an entry that a landing has just made cheaper or more urgent. Move it, and **move it by position rather than by marker** where the repo treats position as priority — the markers mean "faulted" and "needs a decision", and borrowing one to mean "not yet" corrupts the two signals step 3 reads.

**What re-sorting is not.** Reordering an entry is not rewriting what it means, and adding a repair entry is not deciding a design question — a fork still gets queued unanswered for the author. Never delete an entry the author wrote. If moving an entry falsifies a sentence inside it, fix that sentence in the same pass and say so, because the entry's own text often explains its position and goes stale the moment it moves.

## The gardener pass, and it runs every time

**MANDATORY: every run ends with one gardener pass, and a run that closed three or more entries takes one mid-run as well.** A queue drains toward whatever was already in it, so a loop that only ever executes entries leaves the repo tidier and no better aimed. The gardener is a fresh `general-purpose` subagent — **never a `fork`** — whose whole job is to look at what the run actually produced and leave behind a queue pointed at improving the thing the repo measures. It writes entries and it restructures the queue file. It implements nothing.

**It gets two jobs and they are read in this order.** First, **validate what the run landed**: hand it the run's commit range and let it read the diffs against the repo's own rules, looking for the failures those rules exist to catch — a constant or floor added to move a figure, a mechanism the docs do not describe, a lever tuned toward a measurement, a doc left contradicting the code, a figure quoted into a permanent doc that the run's own output does not support. Second, **propose work that would improve runs**: take the outcomes the repo's own docs name as what it is tuned against, read the current findings for which of those are failing, unmeasured, or resting on a stale reading, and write entries that would move them. The second job is the point; the first is what stops it building on sand.

**The hard limits, and they are what make this safe to run unattended.** It may not invent design. **No entry it writes may propose a mechanism the docs do not already describe**, and where it finds that the obvious next step needs a decision, that is a fork: it gets queued unanswered and marked for the author in whatever way the repo marks such things, never resolved and never softened into prose that reads as settled. It may not delete or reverse an entry the author wrote, may not weaken a prohibition list, and may not decide a tuning lever by argument — a lever gets an entry proposing a sweep, not a value. Every entry it writes matches the shape the repo's own entries use, including any rule the repo has about figures, numbering or length. **Aiming at an outcome is not the same as tuning toward it**: an entry that proposes measuring whether a pillar works is inside the line, and one that proposes making a number land is the exact thing the repo's rules forbid.

**Restructuring is allowed and is bounded by the same rules as re-sorting.** It may reorder, group, split an overlarge entry, or rewrite a standing entry's own account of its state — subject to position meaning priority where the repo says it does, to markers keeping their meanings, and to naming in its report every entry it moved with the evidence that moved it. Where a repo forbids numbering its entries, it does not reintroduce numbers.

**Verify before you commit any of it.** Its proposals are claims, exactly as an iteration's report is a claim. Check each defect it names against the code or the doc it points at, and check that each new entry's premise is true — a gardener that misreads a findings section will write a confident entry aimed at nothing. Cut what does not survive that check, keep the rest, and say in the report which you cut. **The queue restructure is its own commit**, separate from any entry's commit, so the run's history keeps executing work and re-aiming the queue distinguishable.

**It never runs concurrently with an iteration.** Both write the queue file, and the loser of that race silently loses its edits. Spawn it only when the tree is clean and the last iteration is genuinely finished — **and "it reported and stopped" is not that**. A pass you resumed once can be resumed again by its own stranded validator, by a queued message arriving late, or by anything else that wakes it, and it comes back writing the same file the gardener now holds. Treat an iteration as finished only when its report has arrived *and* nothing is outstanding that could wake it: no verdict it is still fetching, no message of yours queued against it, nothing of its own left in flight. If you find you spawned the gardener too early, commit whatever the finishing iteration leaves the moment you see it, keep the two sets of edits in separate commits, and never revert either.

## It commits, and here is why

Each closed entry gets its own commit before the next iteration starts. This is not a convenience — the loop does not work without it. `/next-task` validates an entry by handing a subagent `git diff`, so if entry two's work is still sitting uncommitted, the validator checking entry three is reading both and cannot tell which is which. Committing per entry also makes `git log --oneline` the run's record, so no separate journal is needed, and it makes a dirty tree at the start of an iteration mean exactly one thing: the previous entry left work behind.

Match the repo's commit convention — run `git log --oneline -5` and copy what is there. **Never push.** Local commits are cheap to undo; a push is not.

**The gate runs before the commit, and it is the only evidence at that step you did not get from the subagent.** Reading the outcome off the queue file rather than off the report is the right instinct, but it is weaker than it sounds: the subagent that did the work is also the one that edited the file, so both are its output. The repo's gate is not. One command, run by you, on the tree in front of you — that is what makes a closure a fact instead of a claim, and it is cheap because the repo chose it to be cheap. Running it *before* the commit rather than at the next iteration's start is what keeps a broken entry out of history entirely, so the loop never needs to bisect its own commits or revert one.

## Before the first iteration

1. **Read `CLAUDE.md` and find the queue exactly as `/next-task` step 0 does** — that step owns the resolution order, including a `CLAUDE.md` line naming the queue something other than `tasks.md`, so do not keep a second copy of the list here. **No queue means no run:** say where you looked and stop without spawning anything. That is not a fault to recover from, and there is nothing to loop over.
2. **Clear the tree, don't refuse to start.** If `git status --porcelain` returns anything, send a recovery subagent to stash it and carry on once the tree comes back clean. That work may be the author's, so it is preserved and reported, never discarded. The loop needs a clean baseline because every per-entry validation reads `git diff` and would otherwise inherit whatever was already there.
3. **Find the gate and hold the machine cap yourself.** Two things out of `CLAUDE.md`. The gate is the command the repo says a change has to pass — you run it before every commit, so know it before the first iteration and know which kinds of change the repo exempts from it. The cap is whatever the repo says about how much of the machine a run may take: a thread ceiling, a rule against two batches at once, an instruction to check what is already running. **That cap counts every session at once, not every subagent separately.** Your subagents cannot see each other, the author's own work, or a second loop in another terminal, so the checking is yours: run whatever the repo names before each iteration, subtract what is already running, and pass what is left into the subagent's prompt as its budget. A loop that leaves this to each subagent has every one of them believe it owns the machine.
4. Note the starting `HEAD` and the entry headings in file order. The report needs both. **Read back any attempt markers already in the file** — a run that died mid-flight leaves them behind, and they are the part of its ledger that survived.

## Each iteration

1. **Read the state yourself.** Re-read the queue file and run `git status --porcelain`. Carry no claim about the repo forward from the last iteration's report — the file and git are the truth, and a report is only a claim about them. Your own attempt ledger is the exception: that is your bookkeeping, not a claim, and it has to survive the iteration.
2. Check the ending conditions below. If one holds, finish and report.
3. **Target the first entry not carrying `**Needs the author:**`, scanning to the bottom of the file rather than stopping at the first entry that does.** That is the marker `/next-task` writes when it blocks, and it is a fixed string precisely so this step can read it back — match it literally rather than reading the prose around it for intent.
   - **A marked entry is stepped over, never stopped at.** The author is not at the keyboard — that is the whole premise of the mode — so an entry waiting on them cannot move now however long the loop stares at it. Skip it and keep scanning down. A marked entry sitting above takeable work is the commonest way a run ends with the queue still full, and it is a failure of the loop rather than a state of the queue.
   - **A marked entry is not remaining work for any purpose.** Not for selection, not for the ending conditions below, and **not for another entry's precondition about what has to land first**. An entry saying it comes last, or that nothing runs until everything above it has landed, is ordering written against work that can actually land; entries holding the author's marker never land unattended, so they do not hold that gate shut. Read such a precondition against the takeable entries only, take the entry, and say in the report that you read it that way so the author can put it back.
4. **Spawn one subagent, in the background.** `Agent`, `subagent_type: general-purpose`, **never `fork`** — a fork inherits your context, which is the thing this loop exists to avoid. Keep the prompt short: the repo path, which entry it should invoke the `next-task` skill on in `autonomous` mode, and that it should return that skill's step 7 report verbatim. Do not summarize the entry for it, do not say what you expect it to find, and do not pass a loop argument.
   - **Background is the default and the loop depends on it. Never pass `run_in_background: false`.** A synchronous spawn blocks the orchestrator inside a single tool call for as long as the iteration runs, which on a real entry is tens of minutes. Three things break while it is blocked, and all three have bitten this loop: the author cannot steer it, because a message sent mid-iteration is not read until the call returns; a stranded validator's verdict arrives with nobody able to act on it; and the orchestrator cannot do the cheap work that does not need the subagent — checking machine load, verifying a defect against saved output, reading the queue. Spawning in the background costs nothing, since the harness re-invokes you on completion either way. The only thing you may not do while an iteration runs is touch the files it is touching.
   - **Name the entry by its title, never by a number.** A queue that closes its top entry moves every entry under it up, so a position is only true at the moment you read it, and a number in a prompt sends the subagent at whatever now sits there. Repos that forbid numbering their entries do it for exactly this reason.
   - **The `description` says what the work is, never which iteration it is.** That field is the only label anyone watching the run ever sees, and `Work queue entry 3` tells them nothing about what is happening. It is also usually wrong in the one way that matters: closing the top entry leaves the next one at position one, so nearly every iteration reads as entry one and the labels stop distinguishing anything. Take three to five words off the entry's own title — `Portable pow for determinism`, `Delete tag synergy stub`, `Rebuild breeding per specimen`. The same words are what your one-line iteration note below should lead with, so a watcher reads the same name in both places.
   - **Require the close-out before the report, in every prompt.** Say plainly: finish the entry — delete it from the queue and re-point whatever linked to it — and do not end the pass while a validator is still in flight. Left unsaid, a subagent that spawns a validator reliably stops the moment it hands off and reports "waiting on the verdict", which ends the iteration with the work done, the entry still standing, and the validator stranded — it then cannot reach its parent and relays its verdict to you instead. You are left verifying an entry whose own pass never finished, and a good entry risks being charged an attempt for what is a harness quirk rather than a defect. Tell it that if it uses a validator, the verdict comes back to it directly and it acts on the verdict itself.
5. **Verify the outcome from the file, not the report.** Re-read the queue file:
   - **Work complete, gate passing, entry still standing because the pass stopped at its validator → not a fault, and charge no attempt.** This is the shape the rule above exists to prevent, and while it keeps happening it is a quirk of the harness rather than anything wrong with the entry. Commit the work, then either finish the close-out yourself or spend one fresh pass on it — a close-out that only deletes an entry and re-points a link or two is yours to take, and one that has to correct dated prose in a findings or decision log is worth a pass of its own, because the licence to edit that prose is narrow and a fresh reader holds the line better. Say in the report which you did.
   - **Wait for the iteration's agent to actually finish before you commit, even once the queue file says the entry is gone.** A pass deletes the entry and then keeps working — applying its validator's nits, correcting a figure it just re-read. Commit at the moment the file looks done and you capture a state its author is still editing, so their remaining fixes land as a loose diff attributed to whatever runs next, and the agent reports that the loop committed underneath it. The queue file tells you *what* happened; the completion notification tells you *when it stopped*, and you need both. If you find yourself holding a tree that mixes a finished pass's late fixes with a live agent's in-flight work, commit nothing until the live one reports, then split it into one commit each — never bundle them, and never revert either.
   - Entry gone → it closed. **Run the repo's gate yourself before you commit anything.** It passes: commit, one line, matching the repo's convention. It fails: commit nothing, send a recovery subagent to stash the work labelled with the entry, mark the entry with the failure, and continue. Skip the run only where the repo itself says a change of that shape cannot reach what the gate measures, and say why in the report.
   - Entry still there and now carrying `**Needs the author:**` → it blocked. Record the questions for the final report.
   - Entry still there, rewritten or moved → it was stale and got re-sorted, or it was too big for one pass and got split into parts. Commit the queue file edit on its own and continue. **This costs the entry an attempt, exactly as a fault does** — see the rewrite rule below. A pass that produced no code is not progress just because it produced prose, and treating it as free is how one entry gets rewritten indefinitely while the queue looks busy.
   - Entry split into parts → the same, with one difference: the attempt is charged to the entry that was split, and the parts start at zero. A split is only real progress if a part then closes, so if the first part comes back rewritten too, the whole entry is underspecified rather than large.
   - Entry still there and unchanged, but the report claims it closed → a fault. The report and the file disagree; one is wrong and neither is safe to build on. Recover and move on.
6. Check the tree again. Uncommitted work with no entry closed means an implementation was abandoned partway. Commit nothing — that is a fault, and it recovers.

Emit one short line per iteration as you go, so anyone watching can follow without reading the transcript. A fuller summary between iterations is fine too, and running alone does not mean running silently — but it is output, never a checkpoint. Write it and start the next iteration in the same breath; do not end a turn waiting to see whether the author liked it.

**Wait for an iteration's subagent, never watch one.** The harness re-invokes you when it finishes, so there is nothing to poll: no `sleep` loop over `seq`, no grep for `"type":"result"`, no `tail -f`, and no reading the `.output` path the spawn returned — that file is the agent's full JSONL transcript, and reading it floods the context this loop exists to keep empty. Pass this on to any subagent you spawn that will itself spawn one, since a poll loop nested an agent deep is the same waste bought twice. An iteration takes as long as it takes; the notification is the signal, and the queue file and `git` are what you read when it arrives.

**Waiting is not idling, and a background spawn is what makes the difference usable.** While an iteration runs you can read the queue, check machine load before the next spawn, verify a defect a relayed validator has claimed, or answer the author — none of which is possible inside a blocking call. What you may not do is edit a file the running iteration is editing, because its next write will be taken against the version it already read. When there is genuinely nothing to do, say so in one line and stop; do not invent work to fill the wait, and do not commit a tree the live agent is still writing to.

## Faults recover, they do not end the run

**A fault costs the offending entry its turn, never the run.** Keep a ledger of how many times each entry has been attempted. Two attempts is the limit: on the second fault for the same entry, it gets the `**Needs the author:**` marker with the reason written into it, and the loop moves down the queue.

**Write the first attempt into the entry too, not only into the ledger.** One line reading `**Attempted once:**` and what the fault was. An uncapped run is long and the ledger lives in your context, so it dies with the loop — that line is the only part of it a restarted run can read back, and without it the next run starts every entry at zero attempts and pays for the same two faults over again. State that has to outlive an iteration belongs in the file, not in a head, which is the rule the loop already follows everywhere else.

**A rewrite is an attempt, and this is the rule the loop was missing.** An iteration that ends with the entry rewritten, re-sorted or split — and no code — is charged the same as a fault: `**Attempted once:**` goes into the entry naming what the verifier found stale, and it goes in whichever iteration produced the rewrite. On the second such iteration for the same entry, stop believing the entry is merely stale. **An entry rewritten twice is underspecified, not out of date**, and the marker becomes `**Needs the author:**` with one line naming what could not be settled from the entry and the docs it links. Then move down the queue.

**Why this row is the important one.** A stale verdict sends `/next-task` back to select without implementing, by design. So an entry that carries figures which drift, or that describes a change at the level of what it means rather than what it touches, comes back rewritten every single visit — and if a rewrite is scored as progress, nothing ever counts it and the entry sits at the top of the queue being polished for as long as the loop runs. The author sees a growing queue file and no working game. Charging the attempt is what turns that silent circle into two lines in a report.

**`**Attempted once:**` is not the author's-call marker and must never be written as one.** Step 3 keeps selecting an entry that carries it — one fault does not gate an entry, it costs it a turn. On the second fault the line is replaced by `**Needs the author:**` with both reasons under it, and only then does the entry stop being selected.

**You detect and verify; subagents do the work.** Detection is a `git status --porcelain` and a re-read of the queue file, which are cheap and stay with you. Every repair is delegated to a fresh `general-purpose` subagent — never a `fork` — with a narrow brief: the fault, the paths involved, and the preservation rule below. When it returns, **check the tree yourself.** A recovery agent's word that it cleaned up is not evidence the tree is clean. The one write you keep is the per-entry commit, because you have to know exactly what went into it to report it.

**The preservation rule, in every recovery: never discard.** No `git reset --hard`, no `git checkout --` on a file, no `git stash drop`, no deleting a file to make a build pass. Recovery means moving work somewhere labelled and retrievable — a stash with a message naming the run and the entry it came from — and every stash created goes in the final report with its ref. Some of what you stash may be the author's own work.

The faults and what each recovers to:

| Fault | Recovery |
|---|---|
| Tree dirty at the start of an iteration | Subagent stashes it, labelled. Continue. |
| Work uncommitted and no entry closed — an implementation abandoned partway | Subagent stashes it, labelled with the entry. Mark the entry, naming the gap the subagent hit. Continue. |
| Work uncommitted and no entry closed, but the implementation is complete and the gate passes | Not the row above. Commit the code on its own, leave the entry standing with `**Attempted once:**` naming what validation flagged, and continue. |
| The gate fails on a tree where an entry just closed | Commit nothing. Subagent stashes the work, labelled with the entry. Mark the entry with what failed, and continue — the entry did not close, whatever the file says. |
| The report and the queue file disagree about what happened | Believe neither. Treat the entry as not done, stash anything uncommitted, and give it its second attempt with a fresh subagent. |
| An iteration closed nothing, blocked nothing and re-sorted nothing | Second attempt. If it no-ops again, mark it and move down. |
| An iteration rewrote, re-sorted or split the entry and produced no code | Charge the attempt: `**Attempted once:**` into the entry, naming what was found stale. Continue — step 3 still selects it. |
| An entry rewritten twice, whether in this run or according to the marker already in the file | Keep the second rewrite, mark `**Needs the author:**` naming what could not be settled from the entry and its docs, and move down. An entry nobody can stabilise is underspecified, and no third rewrite will find that out. |

**Complete-but-unvalidated is not abandonment, and the gate is what tells them apart.** `git status` reads the same in both, so run the gate before deciding which row you are in. Work that passes it is finished work whose *entry* did not close — usually because a validator kept finding one more stale sentence of prose rather than a defect in the code, which is a report the subagent is right not to close on and wrong to hand upwards as a question. Stashing that is the expensive mistake: a stash holding a landed rewrite conflicts with every later entry that touches the same files, and the loop pays for the same work twice. Commit it, leave the entry standing so the next visit's verifier sees the code is in and closes it in one cheap pass, and say in the report that the entry's code landed unclosed.

**Which of the two markers each row writes.** A row that marks an entry outright — the abandoned implementation, the failed gate — writes `**Needs the author:**` with the reason under it, the same string `/next-task` writes and step 3 selects on. A row that gives the entry a second attempt writes `**Attempted once:**` now and `**Needs the author:**` only if it faults again.

**Nothing in this loop bisects or reverts its own commits.** That path existed to deal with a breakage discovered an iteration after it landed; the gate now runs before each commit, so a broken entry never lands. If the gate is failing at the start of an iteration it is not the loop's doing, and it is a hard stop rather than a fault, below.

Two hard stops, and both are stops because continuing past them produces work that only looks done:

- **The tree will not come clean after two recovery attempts.** The loop cannot validate an entry on a tree it cannot clear, so continuing would produce meaningless passes. Stop, report the exact `git status`, and touch nothing further.
- **The gate fails at the start of an iteration, on a tree the loop has not touched.** Every commit it made passed the gate before landing, so this came from the baseline it inherited or from the stash it cleared. Do not bisect, do not revert, and do not carry on: the next entry's gate run will fail for a reason that has nothing to do with the entry, and grinding forward would mark the whole queue for a breakage none of it caused. Stop and report the exact failure.

## When the run ends

**Whichever way a run ends, [the gardener pass](#the-gardener-pass-and-it-runs-every-time) runs before the report.** That includes a run that closed nothing and a run that stopped on a cap, because a queue nobody could take an entry from is exactly the queue most in need of re-aiming. The two hard stops are the only exception: a tree that will not come clean and a gate already failing both leave the repo in a state where a gardener's reading of it would be worthless.

These are ends, not faults — nothing to recover, and none of them is a failure:

- The queue has no entries left.
- **Every remaining entry carries `**Needs the author:**` — meaning nothing in the whole file is takeable, not merely that the top of it is marked.** Scan to the bottom before concluding this, and treat a marked entry as absent rather than as a wall: if one takeable entry sits anywhere below one that is marked, the run has not ended. Name every skipped entry in the report with what it waits on.
- An iteration cap was given as an argument, and it is reached. With no argument there is no cap, so this is not one of the ways an uncapped run ends — do not stop an uncapped run because it feels long, because several entries have closed, or because a good place to report has come up. Keep taking entries until one of the two conditions above holds, or until a hard stop does.

## Report

Lead with what closed and why the run ended. Then:

- Each closed entry with its commit, and that the gate passed before it landed. Name any entry where the gate was skipped and the repo rule that allowed it.
- **Everything waiting on the author, as the actual questions, in queue order.** This is the part the author is reading for.
- **Every stash the run created, with its ref and what is in it.** Recovery preserves work by moving it out of the way, and a stash nobody is told about is work that is lost in practice.
- Every fault, what it recovered to, and which entries were marked rather than done. A run that recovered four times and closed one entry is not a clean run, and reading like one is the failure mode here.
- Anything re-sorted or split, and where it moved. For a re-sort, the evidence that moved it, so the author can put it back knowing why it went.
- **Every entry the loop added, with the defect that justified it and how you verified that defect.** These are entries the author did not write, so they are read with more suspicion than the rest and have to carry their own evidence.
- **What the gardener pass found and what it left.** Anything it flagged in the run's own landed work, every entry it added with the evidence you checked it against, everything it moved and why, and anything of its output you cut rather than committed. Say plainly which of the outcomes the repo is tuned against are now aimed at by an entry and which are still unaddressed.
- The queue as it now stands, and the range of commits the run produced.

Never spin a recovered fault as a success or a short run as a finished one. If a capped run ended on the second of five iterations, say so in the first sentence. If an uncapped run stopped with un-gated entries still in the queue, that is not an end at all — say in the first sentence why it stopped early and what is left.
