# Homelab architecture

Why the `tom` cluster is shaped the way it is. For what each file declares, read the manifests; this page covers the decisions between them.

## The reconcile chain

Flux applies four `Kustomization`s in a fixed order via `dependsOn`, defined in `clusters/tom/platform.yaml` (platform) and `clusters/tom/apps.yaml` (apps):

`infra-platform-crds` → `infra-platform-controllers` → `infra-platform-configs` → `apps`

Each stage produces the API types or running controllers the next one needs, so the order is a hard dependency, not a preference:

| Stage | Path | Produces | Next stage needs it because |
|-------|------|----------|-----------------------------|
| crds | `infrastructure/platform/crds` | Gateway API CRDs + Traefik gateway RBAC | controllers install resources of these kinds. |
| controllers | `infrastructure/platform/controllers` | external-secrets, cert-manager, MetalLB, Traefik, Longhorn (Helm) | configs are custom resources those controllers own. |
| configs | `infrastructure/platform/config` | `ClusterSecretStore`, `ClusterIssuer`, MetalLB pools, Traefik service, Longhorn `StorageClass` + gateway | apps consume all of these. |
| apps | `apps/tom` | pihole, gnosis | — |

- The first three stages set `wait: true`, so Flux blocks until each is *Ready* — CRDs established, HelmReleases healthy — before starting the next. This trades a slower first bootstrap for a deterministic one: a config CR applied before its controller exists would only error and retry-loop.
- Ordering is enforced by `dependsOn`, not filesystem layout — the split into `crds` / `controllers` / `config` directories mirrors the three phases so the boundary is obvious.
- cert-manager's own CRDs ship with its Helm chart (`crds.enabled: true`), so only Gateway API CRDs need the dedicated first stage.
- **The Gateway API bundle version is coupled to Traefik's minor version.** Traefik pins the spec version it supports (v3.7 → Gateway API v1.5, standard channel — check the shipped Traefik image version, not the chart docs, which can lag) and its provider silently stops programming Gateways when a CRD it watches is missing — the symptom is every `Gateway` stuck at `Waiting for controller` and Traefik serving its default self-signed certificate. Bump the `standard-install.yaml` URL in `crds/gateway-api/` in the same change as any Traefik chart major.

## Secret flow

No plaintext secret lives in git. Secrets are pulled from 1Password at runtime by the External Secrets Operator (ESO):

1. One bootstrap secret is seeded by hand: `1password-service-token-tom` (a 1Password service-account token) in the `external-secrets` namespace. This is the single trust root.
2. `ClusterSecretStore/1password` (`config/1password-cluster-secret-store.yaml`) uses that token via the 1Password SDK to read the `Homelab - Tom` vault.
3. `ExternalSecret`s reference the store and materialize native Kubernetes `Secret`s (`creationPolicy: Owner`) — e.g. `pihole-web-password`, the Cloudflare API token for cert-manager, and the Discord webhook for Flux alerts.

Decisions:

- **One human-provided secret.** Everything else derives from the vault, so rotating a credential happens in 1Password and propagates on the next sync — nothing to re-commit.
- **ESO must be up before any `ExternalSecret`**, which is why external-secrets is a controller (stage 2) and the store is a config (stage 3).
- **No `ExternalSecret` may live in `clusters/tom/`.** The flux-system Kustomization dry-runs everything it applies, so on a fresh cluster an `ExternalSecret` there fails validation before ESO's CRDs exist and deadlocks the entire chain at bootstrap. The Discord-webhook `ExternalSecret` therefore lives in the config stage (`config/flux-discord-webhook.yaml`); `alerts.yaml` keeps only the `Provider`/`Alert`, whose CRDs ship with Flux itself.

## Ingress and TLS

Every web app is reached over HTTPS at `<app>.dloez.dev` through the same four pieces:

- **MetalLB** (L2) hands out LAN IPs from a pool (`config/ip-pools.yaml`). Bare metal has no cloud load balancer, so MetalLB fills that role. `traefik-custom` pins `192.168.1.19` as the single ingress entrypoint; pihole's DNS service pins `192.168.1.18`.
- **Traefik** is the `GatewayClass` (`gatewayClassName: traefik`). It runs with the Kubernetes Gateway provider **on** and the legacy Ingress provider **off** — the cluster is Gateway-API-only. Traefik's built-in service is disabled in favor of the explicit `traefik-custom` service so the MetalLB IP is declared, not guessed.
- **cert-manager** issues a per-host certificate through `ClusterIssuer/cloudflare-issuer` (Let's Encrypt ACME, **DNS-01** via Cloudflare). DNS-01 was chosen over HTTP-01 so certificates issue without exposing an inbound HTTP challenge endpoint.
- Each app declares a `Gateway` (a `web`/HTTP + `websecure`/HTTPS listener) and `HTTPRoute`s. HTTP→HTTPS is redirected twice over: a Traefik entrypoint redirect (`web`→`websecure`) and a per-route `RequestRedirect` (301). The Gateway terminates TLS with the secret cert-manager wrote.

Why Gateway API over Ingress: it is the successor API, keeps routing — redirects, path rewrites like pihole's `/`→`/admin` — declarative and portable, and avoids Traefik-proprietary CRDs.

## Image automation

pihole's container tag is updated by Flux, but changes land through a reviewed PR, never a direct push to `main`:

1. `ImageRepository/pihole` scans `docker.io/pihole/pihole` every 5m.
2. `ImagePolicy/pihole` picks the newest CalVer tag (`YYYY.MM.RELEASE`, alphabetical ascending).
3. `ImageUpdateAutomation` rewrites the tag on the line marked `# {"$imagepolicy": "flux-system:pihole"}` in `apps/tom/pihole.yaml` (Setters strategy) and pushes it to the branch **`image-automation-tom-pihole`** — not `main`.
4. CI turns that branch into a titled, `dloez`-assigned PR; on merge Flux reconciles `main` and rolls pihole forward, and CI deletes the branch. Branch naming is `image-automation-<cluster>-<app>` — see the [general CI reference](../../general/reference/ci.md).

Decisions:

- **PR-gated, not auto-merged.** A homelab still wants a human glance at an image bump before it hits the only DNS server on the network.
- The `image-automation-<cluster>-<app>` convention encodes enough for CI to generate the PR title and to scope branch cleanup.

## The gnosis staking app

`apps/tom/gnosis.yaml` runs a Gnosis Chain validator: Nethermind (execution) + Lighthouse beacon (consensus) + Lighthouse validator client, deposit flow in the [how-to](../how-to/deploy-gnosis-validator.md). Its shape breaks a few repo habits on purpose:

- **Not pinned to a node — the control-plane taint does the placement.** With `controlplane1` tainted `NoSchedule`, worker1 is the only schedulable node, which keeps the chain database on the node that physically holds its Longhorn replica. If a second worker ever joins, enforce locality with Longhorn `dataLocality: strict-local` rather than pod pinning — a chain DB attached over iSCSI from another node falls behind chain head.
- **`replicas: 1` + `strategy: Recreate` + doppelganger protection on the validator client.** Two live signers with the same key is the one slashable offence. This workload must never be made "highly available" — the rolling-update overlap of a default Deployment is exactly the failure mode.
- **p2p over `hostPort`** (30303 execution, 9000/9001 beacon) instead of a MetalLB service: peers need the node's real address, and one worker means no scheduling constraint cost. Inbound peering also works without router port-forwards (outbound dialing suffices), just with fewer peers.
- **No Gateway/HTTPRoute.** Nothing here is a web app; the engine and beacon APIs stay cluster-internal.
- **Key material follows the standard ESO flow** — keystores, password, JWT, and fee recipient live in the 1Password vault and materialize as Secrets. The mnemonic that generated the keys never touches the cluster or 1Password; it exists only on paper.
- **Nethermind runs with raised ancient barriers (`Sync.AncientBodiesBarrier` / `Sync.AncientReceiptsBarrier`), which is what keeps the execution DB inside its 400 Gi volume.** Nethermind's default barrier sits at the deposit contract deployment block, so a default node backfills every post-deposit-contract body and receipt — on Gnosis that is ~22 M blocks and overruns 400 Gi before the backfill even finishes, crash-looping the client on `Not enough free disk space in '/data'`. That default exists because consensus clients used to rebuild their deposit Merkle tree by scanning deposit-contract logs; EIP-6110 (live on Gnosis since Pectra) moves deposits on-chain as execution requests and retires that scan. Historical bodies and receipts contribute nothing to attestation, proposal, or sync-committee rewards, so the barriers are raised to a recent block and the node keeps only a rolling recent window. Raising the barrier does **not** delete history already on disk — there is no in-place prune for ancient bodies, so changing it means wiping the volume and re-syncing. The barriers cover bodies and receipts **only**; there is no equivalent barrier for headers, because the header chain must be complete to validate. `Old Headers` therefore still backfills to genesis on every fresh sync — ~47.6 M headers on Gnosis, a few hours on this hardware — and seeing it run is expected, not a sign the barriers failed to apply.
- **A nethermind restart resets the snap-sync *counters*, not the downloaded state — it costs time, not data.** Observed on 2026-08-06: a rolling restart dropped `Snap State Ranges (Phase 1)` from 31.56% to ~4% and `nethermind_snap_synced_accounts` from 3.5 M to 0.5 M. Both are process-lifetime counters initialised at start-up, not persisted progress, so the drop is a display artefact. The state itself stays in the `state` column family and is re-written with identical keys as the ranges are re-walked, because the key is a function of the pivot's state root and the pivot (`47589108` here) is persisted and unchanged. Nothing is orphaned and no cleanup is needed: measured over five minutes with the counter at 12.5%, used space on the volume *fell* ~0.9 GB while snap advanced 1.8 pp and 1.3 M headers landed — RocksDB compaction collapsing superseded versions faster than new data arrived. The real cost of a mid-sync restart is the re-download and the write amplification it triggers, so still batch config changes into one reconcile, but a restart is not the disaster a collapsing progress bar makes it look. The one case that *does* orphan data is a restart that selects a **new** pivot: a different state root means different keys, and the old nodes then sit unreferenced until pruning reclaims them.
- **After an outage of more than ~20 minutes the two clients can lock into a loop that never converges: the beacon range-syncs the gap one block per `forkchoiceUpdated`, and nethermind treats every one of those as a new beacon pivot that costs a ~5 s peer round-trip — so the pair advances exactly one block per 5 s slot and the distance stays constant.** Observed 2026-09-15 after the storage stall: the beacon flew through the first ~1,200 slots at 5 slots/s while nethermind was still replaying its own tail, then dropped to `0.20 slots/sec` and held at ~245 slots for over an hour. Nethermind's log is the tell: `Syncing, Block 0x… not found` → `New beacon pivot` → `Start a new sync process` every 5 s with consecutive block numbers, while the beacon reports `SyncingFinalized` on `/lighthouse/syncing` and issues one forkchoice per block instead of per batch. Restarting either client only replays the same loop. What works is to move the beacon's head *past* nethermind in one jump — checkpoint-sync it again with `--purge-db --purge-db-force` — after which nethermind receives a pivot ~250 blocks ahead, fetches that range in one sync cycle at ~8 blocks/s, and both are at head within five minutes. Steps are in the [storage-stall how-to](../how-to/recover-worker-storage-stall.md); the purge is safe because the beacon holds no keys and Lighthouse rebuilds history by backfilling.
- **Nethermind interleaves the header backfill and snap state ranges, so neither has a steady rate.** `Old Headers` and `Snap State Ranges` take turns; a Phase 1 percentage can sit still for many minutes while headers run at several thousand blocks per second, then jump. Sampling either over a short window gives a rate that is badly wrong in both directions — measure over tens of minutes before drawing an ETA from it.
- **The beacon volume is sized for a non-archive node (100 Gi).** Without `--genesis-backfill`, `--archive`, or `--reconstruct-historic-states`, Lighthouse backfills only to the most recent weak-subjectivity checkpoint, and v8's tree-states storage keeps a staking node's database far below the volume size. Longhorn thin-provisions, so an oversized claim wastes scheduling headroom on `persistent-cluster-data` rather than physical disk — but since Longhorn can expand a volume and never shrink one, size these claims at the real working set and expand if wrong.

## Storage

Longhorn provides dynamic block storage. The default `StorageClass`, `longhorn-single-replica`, sets `numberOfReplicas: 1`.

- With a **single worker**, cross-node replication is impossible — extra replicas would only duplicate data on the same disk. One replica is the honest setting and saves space.
- Trade-off: no in-cluster redundancy; losing the worker's disk loses volume data. Acceptable for a homelab, and the worker reserves an 895 GB Talos user volume (`persistent-cluster-data`) for it.
- **`engineReplicaTimeout` is raised to 30s (default 8s) because a single NVMe stall takes down every volume at once.** All replicas for all volumes run inside the one `instance-manager` process on worker1, and worker1's system disk (a DRAM-less QLC drive) can stall long enough under sustained write load for the NVMe driver to time out an admin command and reset the controller — observed once on 2026-08-06, roughly 38 minutes after ~550 Gi of volumes were deleted, when the resulting TRIM/garbage-collection storm overlapped a fresh chain sync. Every volume lost its backing device simultaneously, ext4 journals aborted, and Longhorn auto-salvaged all three — taking pihole and the Longhorn UI down alongside the workload that caused it. With `numberOfReplicas: 1` there is no second replica to absorb this, so the timeout is the only cushion. Symptom to recognise: `nvme nvme0: ... QID 0 timeout, reset controller` in `talosctl dmesg`, and clients misreporting it as database corruption. **The setting is read when an engine process starts, not when the setting changes** — a volume that was already attached keeps the timeout it was launched with, so `kubectl -n longhorn-system get settings.longhorn.io engine-replica-timeout` can read 30 while the running engine still has `--engine-replica-timeout 8`. Confirm the value actually in force with `kubectl logs -n longhorn-system <instance-manager> | grep -o 'engine-replica-timeout [0-9]*'`; picking up a new value needs the volume detached and reattached, which means restarting the workload that mounts it.
- **The same drive can also stall *silently* — no NVMe timeout, no controller reset — and then `engineReplicaTimeout` is no cushion at all, because the whole node's I/O is wedged, not just one replica.** Observed 2026-09-15 at ~16:25 UTC after eight days of steady duty (no volume churn this time): every write to the three Longhorn iSCSI devices (`sda`/`sdb`/`sdc`) hung for ~60s and then failed with `critical medium error ... Unrecovered read error`, which is what the Longhorn engine returns once it has no replica left to serve I/O, and all three ext4 journals aborted and remounted read-only. Unlike the 2026-08-06 case, `talosctl dmesg` shows *nothing* from the `nvme` driver, and the drive's SMART `NumErrLogEntries` ticked up by exactly one across the incident — the controller stopped completing commands without the kernel ever declaring a timeout. The tell that distinguishes it from a Longhorn-only fault: the node's own XFS partitions were stuck too — `talosctl read /var/log/pods/...` and even `talosctl ls -l` on the log directory hung, kubelet answered `/healthz` and `/stats/summary` but `kubectl logs`/`exec`/`port-forward` timed out, per-container I/O PSI `full` read 96-99% for anything touching a volume, the kubelet logged `failed liveness probe, will be restarted` for the beacon once a minute for two hours without a single restart landing (the process was unkillable in D state), and `longhorn-manager`'s own log simply stopped four minutes before the volumes failed. Nothing short of a power-cycle recovers it — a graceful `talosctl reboot` cannot unmount the stuck filesystems. Longhorn auto-salvaged all three volumes on the way back up, ext4 mounted them read-write without a fsck pass, and the chain clients resumed from their last committed state (Nethermind re-ran ~230 blocks, the beacon head-synced the gap at ~5 slots/s). Procedure: [Recover worker1 from a storage stall](../how-to/recover-worker-storage-stall.md). The durable fix is a drive with DRAM/PLP or a second node so `numberOfReplicas` can be 2; until then, expect this to recur and treat validator downtime as the alarm.
- **The chain clients set CPU *requests* but no CPU *limit*; memory limits stay.** An earlier revision capped nethermind at 2 cores and the beacon at 1 to leave headroom on worker1's 4 cores (3950m allocatable). Measured during a snap sync on 2026-08-06, that cap held nethermind in CFS throttle for 57.9% of its scheduling periods and the beacon for 10.9% while the node still had ~0.8 cores idle — a CPU limit throttles a cgroup even when nothing else wants the CPU. It also made the reported load average *worse* rather than better, because throttled threads stay runnable and keep counting toward load, and it starved the beacon's HTTP API badly enough that its own validator client logged ~6 failures per minute of `Unable to read spec from beacon node` and `No synced beacon nodes`. Gnosis's 5-second slots leave only ~1.67s to validate a payload before the attestation deadline (mainnet allows 4s), so client latency costs the head vote — 14 of an attester's 54 reward weight — and a validator client that cannot reach its beacon misses source and target too, which *are* penalised. Requests still guarantee a proportional share under contention, which is the protection that actually matters; memory limits stay because an OOM cascade is a real failure mode where CPU throttling is only a latency tax.
- **The beacon's memory *request* is sized to its real usage, because the request is what sets eviction order.** The kubelet ranks Burstable pods for eviction by usage *above request*, so the original `requests: 2Gi` against ~3.3 GB of actual use made the beacon the node's top eviction candidate — the single workload the cluster exists for, ranked most disposable — while nethermind sat safely *under* its 4Gi request once reclaimable page cache is excluded. Now `requests: 4Gi` / `limits: 6Gi`, which — with nethermind's raise below — puts node memory requests at ~72% of allocatable.
- **The beacon leaks ~0.86 GiB/hour during data-column backfill; the memory *limit* only sets the crash interval, it does not prevent the crash.** This is a known upstream bug, called out in Lighthouse's own v8.2.1 release notes: _"Data column backfill can OOM, particularly on Gnosis chain. This is fixed on `unstable`."_ Measured on 2026-08-07: the beacon started at ~1.2 GiB and was OOMKilled at 6.0 GiB 5h33m later, having grown linearly with no plateau. So 4Gi buys ~3h between crashes, 6Gi ~5.5h, 8Gi ~7.5h — raising the ceiling only buys time. Do **not** try to fix this by shrinking `--state-cache-size`: measured on the same day, growing the cache from 65 to 90 states cost 20 MB total (~1 MB per state), because v8's tree-states storage shares unchanged subtrees between consecutive states. The state cache is not the consumer, and cutting it would trade attestation latency for nothing. Two traps this episode set, both of which caught us: sampling memory over minutes shows oscillation (5.46–5.55 GiB) that hides an hourly trend, and dividing total RSS by a cache's item count silently assumes the items are independent. **Resolved on 2026-08-07 by moving the beacon onto the `unstable` build that carries the fix — see the next bullet.**
- **The beacon runs a pinned `unstable` image *digest* rather than a release tag, and that is what allowed the restart `CronJob` to be deleted.** Lighthouse merged [#9665](https://github.com/sigp/lighthouse/pull/9665) (`Clean up custody backfill requests after peer failures`) into `unstable` on 2026-07-20, one day before v8.2.1 was cut from `stable`, so the newest release does *not* contain the fix for the leak above and v8.3.0 is the first that will. Sigma Prime publish no commit-SHA tags, only the floating `latest-unstable`, so the pin is the multi-arch manifest digest `sha256:3a3009…6689c` — the 2026-08-07T07:23Z build, 18 days of `unstable` past the fix. Pinning by digest instead of tag is the entire point: `latest-unstable` is rebuilt on every merge to `unstable`, so a tag reference would silently move the node onto arbitrary development code on any image pull, which is a worse failure mode than the bug being fixed. Only the beacon moved — the validator client stays on the v8.2.1 release tag, because the signing component has no reason to leave a tested release and Lighthouse supports beacon/validator version skew.
- **The deleted `gnosis-beacon-restart.yaml` is restorable history, and the dependency runs both ways.** It held a `CronJob` plus a ServiceAccount and Role scoped by `resourceNames` to the one deployment it could patch, restarting the beacon every 4 hours so the inevitable crash was graceful rather than a SIGKILL. Measured on 2026-08-07: a graceful rollout took the beacon out for ~30s and cost **0** attestations, while the OOMKill took ~180s and cost **2** — SIGKILL leaves the database unclean, so the next start does recovery work before it serves. In reward terms that difference is negligible (~0.8% of a 1 GNO stake's yield, i.e. fractions of a cent), so rewards were never why it existed; it existed because ~4 unclean database shutdowns a day, on a single-replica Longhorn volume, on the DRAM-less QLC drive documented above, repeatedly pokes the one component already known to abort ext4 journals under stress. **If the beacon is ever reverted to a build without #9665, restore the CronJob in the same change** — and once v8.3.0 ships, return the beacon to a release tag, since running `unstable` is a time-boxed measure, not architecture. It also carried a second cost worth remembering: `kubectl rollout restart` stamps `kubectl.kubernetes.io/restartedAt` on the pod template, which is drift Flux reverts on its next reconcile, so every fire restarted the beacon **twice** — once for the CronJob and once for the revert ~10 minutes later. A workaround that mutates a Flux-managed object fights the reconciler by construction; `kubectl delete pod -l app=…` would have been the non-mutating equivalent.
- **Read `anon` from `memory.stat`, not `memory.current`, before calling a container memory-starved.** `memory.current` counts reclaimable page cache, so a healthy RocksDB client always reads as nearly full: nethermind sits at 7.50 GB of its 7.52 GB limit (99.8%) while only 2.64 GB is `anon` — the other 4.48 GB is page cache, of which 4.24 GB is `inactive_file` and evictable on demand, and `memory.events` shows `oom_kill 0`. The high `max` count in `memory.events` is ordinary reclaim at the cgroup boundary, not distress. Acting on the 99.8% by shrinking `Init.MemoryHint` or `Pruning.CacheMb` would be actively harmful, pushing reads onto the QLC drive that is already the node's real bottleneck. Cross-check against the node before concluding anything: on 2026-08-07 the host had 7.05 GiB `MemAvailable`, no swap, and `/proc/pressure/memory` flat at 0.00 across all windows while `/proc/pressure/io` ran `some avg300=3.66%` at only 0.4 MB/s of throughput — latency-bound I/O, not memory shortage, and the actual cause of the engine-API timeouts that cost 24 consecutive epochs that morning.
- **Ordinary reclaim is still not free on this drive: nethermind went to `requests: 6Gi` / `limits: 10Gi` on 2026-08-13 and it bought ~4 points of head vote.** The bullet above is right that `memory.events`' `max` counter is reclaim at the cgroup boundary rather than OOM distress, and right that shrinking `Init.MemoryHint` or `Pruning.CacheMb` would be harmful — but the inverse move was never tried, and the ceiling was binding. At 7Gi, nethermind held ~3.8 GiB of page cache for a 178 GiB RocksDB while `max` incremented ~640 times per 10 minutes and `io.pressure full avg300` sat at 9.40%, because every evicted page is a re-read of the DRAM-less QLC drive. Measured on clean before/after windows while the validator held a sync-committee slot: sync-committee head votes 81.3% (n=1057) → 85.6% (n=583), blocks whose head was still unset at the per-slot summary 10.9% → 7.2%, `io.pressure full avg300` 9.40% → 4.10%, and the `max` counter stopped incrementing altogether (0 in 25 minutes). The lesson is to read the *rate* of `max` against `io.pressure`, not the absolute count — a `max` count that climbs while I/O stalls is a cache too small for its drive, whereas a static one is the harmless boundary reclaim described above.
- **A running container's memory can be resized without restarting it, which is how the raise above landed mid-duty.** `kubectl patch pod <pod> --subresource resize` is honoured in place by the kubelet when `resizePolicy` is unset, because it defaults to `NotRequired`; `restartCount` and `startedAt` were unchanged across the change, so a validator holding a sync-committee slot never lost a signature. Memory *increases* are the safe direction — decreases are best-effort and may need a restart. The catch is that this edits the **Pod**, not the Deployment: Flux does not revert it because Flux does not own Pods, but the next pod recreation silently restores the manifest's value, so the same numbers must be committed to `gnosis.yaml` or the fix quietly disappears at the next restart.
- **After the memory raise the binding constraint is data availability, not execution — measured 2026-08-13.** Lighthouse's per-block gauges across 77 consecutive blocks put `execution_time` at p50 174ms / p90 1212ms but `available_slot_start` at p50 1037ms / p90 1722ms, against Gnosis's 1667ms signing deadline — so ~12% of blocks turn attestable too late no matter how fast the payload validates, and further EL tuning cannot reach them. Two components: a ~570ms gap between full verification finishing and the block becoming available, which is PeerDAS data-column work rather than EL latency, and a cluster of ~12% of blocks first *observed* at ~1440ms. `--disable-backfill-rate-limiting` is not the lever: rate limiting is already the default, and Lighthouse's help tells stakers to keep it because backfill is not required for staking.
- **That ~1440ms cluster is the network publishing late, not this node processing late — do not spend more time on it.** Confirmed two independent ways on 2026-08-13. First, `beacon_data_column_gossip_slot_start_delay_time`'s buckets carry the identical bimodal shape as the block delays: 78% of custody columns land inside 300ms, then nothing until a tight band of 13.9% between 1.25s and 1.5s — blocks and their columns arrive late *together*, which no local processing artefact would produce. Second, decoding the `SyncAggregate` of block N+1 gives network-wide participation for slot N for free, and on the slots this validator voted stale it reads mean **87.5%** against **95.3%** on the slots it got right, a −7.7pp drop that says those slots were objectively harder for everyone. The uncomfortable half of that result is that 87.5% of the committee still voted them correctly while we did not: a block landing at 1.44s leaves ~227ms to the 1667ms deadline, and this node's full verification alone is p50 309ms. The misses are not caused by a defect to find — they are the slow tail of a node whose import path does not fit the budget that late blocks leave, and the remaining levers are the drive and the core count, not configuration. Two dead ends recorded so they are not retried: the proposers are not the pattern (55 stale slots, 55 distinct proposers, zero repeats), and the apparent hard ceiling near the deadline is survivorship — blocks published later than the attestation deadline lose the fork-choice race and never become head, so a canonical-block sample cannot contain them.
- **Most platform controllers run BestEffort and yield first under contention.** MetalLB, cert-manager, and the Longhorn CSI sidecars set no requests, so an unbounded chain client will squeeze them before anything else. Longhorn's `instance-manager` is the exception that matters and carries its own 474m request, keeping a guaranteed share of the disk path the chain DB sits on. MetalLB's `speaker` is the one to watch, since it answers ARP for the LoadBalancer IPs — the `frr` container's restart count is cosmetic here because the pools use `L2Advertisement`, not BGP, so `frr` is not in the data path.
- **The `persistent-cluster-data` disk is registered with Longhorn imperatively, not via GitOps** — Longhorn's `Node` CR is created at runtime by the manager, so the disk is added by a `kubectl patch` in the [bootstrap how-to](../how-to/bootstrap-cluster.md) (step 7). This is the one post-bootstrap manual step besides the 1Password token seed; forgetting it faults every PVC larger than the 100 GB default disk.
